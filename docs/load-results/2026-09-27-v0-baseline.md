# v0 baseline, 27 September 2026

The first load runs against the deliberately naive baseline (see ADR 5). Nothing has been tuned.
Raw k6 summaries for every run are in `load/results/`.

## Setup

Everything on one laptop (Windows 11 Home), which is the main caveat: k6, the API and PostgreSQL share
the same CPU, so absolute numbers are only comparable with other runs on this machine.

| Component | Detail |
|---|---|
| API | `dotnet run -c Release`, Development environment, Kestrel on http://localhost:5080 |
| Database | PostgreSQL 18.6 native install, default `max_connections = 100` |
| Connection pool | Npgsql defaults (`Max Pool Size = 100`) |
| Data | Deterministic seed: 20,000 students, 121 modules, 80,000 enrolments, 80,000 grades |
| Load generator | k6 2.2.0 on the same machine |

## Run 1: enrolment rush

`load/k6/enrolment-rush.js`: 500 virtual users, one request each, all fired at once at `POST /students/{n}/enrolments`
for module CS3099, which has 30 places.

| Metric | Value |
|---|---|
| Places available | 30 |
| Enrolments accepted (HTTP 201) | 154 |
| **Oversold** | **124** |
| Rejected as full (HTTP 409) | 84 |
| Errored | 262 |
| Requests refused at TCP level (never reached the app) | 260 |
| `http_req_failed` | 69.06% |
| p95 latency (of requests that connected) | 729 ms |

Three separate failure modes in one run:

1. **Lost update / check-then-act race.** Every request reads the current count, sees fewer than 30, and inserts.
   Nothing serialises the check and the write, so 154 requests all "saw" a free place.
2. **Database connection exhaustion.** The API log shows Postgres error `53300: remaining connection slots are
   reserved for roles with the SUPERUSER attribute`. The Npgsql pool is allowed 100 connections and Postgres
   allows 100 minus its reserved slots, so the pool can legitimately ask for more than the server will give.
3. **TCP connections refused.** 260 of 500 connections got `connection refused` from the OS before Kestrel saw
   them. Most likely the listen backlog overflowing under 500 simultaneous connects; to be confirmed.

## Run 2: results day

`load/k6/results-day.js`: arrival-rate ramp 10 → 50 → 300 → 800 → 800 → 0 requests per second over 4.5 minutes
against `GET /students/{n}/dashboard`, random student each time.

| Metric | Value |
|---|---|
| Requests | 104,399 |
| Peak arrival rate | 800 /s |
| `http_req_failed` | 0.00% |
| p95 latency | 6.52 ms |
| p99 latency | 15.59 ms |
| Max latency | 358 ms |
| Peak concurrent virtual users | 12 |

**It did not collapse.** The dashboard does roughly 15 queries per request (student, enrolments, then one
module query and one timetable query per enrolment, then grades, then one module query per grade). With
PostgreSQL on the same machine each query is a fraction of a millisecond, so the whole thing costs about 4 ms
and 800 requests per second needs only a dozen connections. The N+1 pattern is real, but it is only expensive
when there is network latency between the API and the database. That experiment is next.

## Run 3: where does the dashboard break?

`load/k6/dashboard-knee.js`: hold a constant arrival rate for 30 seconds. `dropped_iterations` counts requests
k6 wanted to send but could not, because every virtual user was still waiting on a slow response.

| Target rate | Achieved | Failed | p50 | p95 | p99 | Max | Dropped |
|---|---|---|---|---|---|---|---|
| 1,000 /s | 870 /s | 10 (0.04%) | 5 ms | 2.49 s | 3.06 s | 5.3 s | 2,935 |
| 2,000 /s | 697 /s | 1,931 (8.3%) | 5.70 s | 7.33 s | 7.74 s | 11.4 s | 36,723 |
| 3,000 /s | 919 /s | 6,144 (19.9%) | 1.59 s | 8.27 s | 8.71 s | 10.2 s | 59,153 |
| 4,000 /s | 711 /s | 4,204 (16.2%) | 6.18 s | 8.21 s | 8.63 s | 9.8 s | 94,100 |

Three things to read off this table:

- **The knee is sharp and sits between 800 and 1,000 requests per second** on this laptop. At 800 the p95
  is 6.5 ms; at 1,000 it is 2.5 seconds. Median stays at 5 ms because most requests are still fine; the tail
  is where saturation shows first.
- **Throughput has a ceiling of roughly 700 to 900 requests per second regardless of offered load.** Past
  the knee, offering more does not get more; it gets less, because the server spends its time on requests
  that will time out anyway.
- **Connection exhaustion returned.** Postgres error 53300 was logged 417 more times during this probe. Under
  sustained saturation the dashboard's dozen connections became a hundred, and Postgres said no.

A small number of TCP refusals (a few tens per 30-second run) also appeared at 2,000 requests per second
and above, the same symptom as run 1 at a much lower intensity.

## What this changes

- The enrolment race is the first thing to fix (correctness bug, not a performance one).
- The connection pool must be sized below what Postgres will actually grant, and pool-wait failures should
  turn into fast, clear errors rather than 500s.
- The server needs a way to shed load once it is saturated (concurrency limit or queue with a bound), so
  that offering 4,000 gets a fast "try again" for the excess rather than a slow failure for everyone.
- The dashboard needs a realistic database round-trip before its N+1 can be judged. Planned: run PostgreSQL
  with injected latency (2 to 5 ms) and repeat runs 2 and 3.
- Confirm the TCP refusal cause (listen backlog vs. something else) before touching it.
