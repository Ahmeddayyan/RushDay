# v1 hardened, 2 October 2026

The same four stories as the [v0 baseline](2026-09-27-v0-baseline.md), run against v1 on the same laptop. Raw k6
summaries are in `load/results/` (the `20261002` files) and labelled in `load/results/runs.json`; the `/story` page
renders them through `load/summarize.mjs`.

## Setup

| Component | v0 (27 September) | v1 (2 October) |
|---|---|---|
| Machine | One laptop: Windows 11 Home, 8-core/16-thread Intel Core i7, 16 GB | Same laptop |
| API | `dotnet run -c Release`, Development, http://localhost:5080 | Release single-file publish (`scripts/run-api.ps1` style), Development configuration as `docs/spec/04-performance-and-ops.md` section 9 prescribes, http://localhost:5112 |
| Database | PostgreSQL 18.6 native, `max_connections = 100` | Same server |
| Database role | Owner | `rushday_app`, the least-privilege role of `docs/deployment.md` section 6; migrations on the owner (`ConnectionStrings__Migrations`) |
| Pool and limits | Npgsql default pool 100; no limits | Pool 40; concurrency limiter 64 + queue 1,024; per-user limits relaxed (`appsettings.Development.json`) |
| Data | Deterministic seed: 20,000 students | A `CREATE DATABASE ... TEMPLATE rushday` clone of that same v0 database, migrated and backfilled by v1 on start (the production upgrade path). A fresh clone for every enrolment rush and login-storm run, one clone for the four knee runs |
| Load generator | k6 2.2.0, same machine | Same; every scenario signs its students in during `setup()` in batches, so latency below is the measured endpoint alone, not the logins |

The main caveat is unchanged: k6, the API and PostgreSQL share one CPU, so absolute numbers only compare with other
runs on this machine, and nothing here predicts Render's 0.1 vCPU. The Development limits (queue 1,024, pool 40) are
looser than production's (queue 96, pool 20); the production limits were not load-tested here.

## Run 3: where does the dashboard break? (30 s at a fixed rate)

| Offered | | Served 200 | Shed 503 | Transport failures | Dropped | p50 | p95 | p99 | Max |
|---|---|---|---|---|---|---|---|---|---|
| 1,000/s | v0 | 870/s achieved, 10 failed (0.04%) | – | – | 2,935 | 5 ms | 2.49 s | 3.06 s | 5.3 s |
| | v1 | 29,952 (≈1,000/s) | 0 | 49 refused | 0 | 4.4 ms | 464 ms | 641 ms | 711 ms |
| 2,000/s | v0 | 697/s achieved, 8.3% failed | – | – | 36,723 | 5.70 s | 7.33 s | 7.74 s | 11.4 s |
| | v1 | 30,668 (≈1,020/s) | 28,028 | 1,306 | 0 | 876 ms | 1.26 s | 1.48 s | 1.70 s |
| 3,000/s | v0 | 919/s achieved, 19.9% failed | – | – | 59,153 | 1.59 s | 8.27 s | 8.71 s | 10.2 s |
| | v1 | 14,282 (≈476/s) | 72,682 | 2,859 | 179 | 75 ms | 1.50 s | 6.22 s | 7.79 s |
| 4,000/s | v0 | 711/s achieved, 16.2% failed | – | – | 94,100 | 6.18 s | 8.21 s | 8.63 s | 9.8 s |
| | v1 | 5,271 (≈176/s) | 49,035 | 49,318 | 16,378 | 625 ms | 1.90 s | 10.7 s | 17.6 s |

v1 latency columns are every dashboard request (200, 503 and failures together). From the API's own log, the
503s were answered in 7.0 / 4.3 / 1.5 ms at p95 for 2,000 / 3,000 / 4,000 requests/s (p99 26 / 22 / 18 ms).
Postgres `53300` appeared **zero** times at every rate (v0: 417 more during this probe).

What this shows, and what it does not:

- **1,000/s, v0's knee, is no longer a knee**: every request served, p95 464 ms against v0's 2.49 s.
- **At 2,000/s v1 sheds instead of collapsing**: about 1,020 served per second, the excess answered 503 within
  milliseconds, and nothing slower than 1.7 s, against v0's 5.7 s median and 11.4 s maximum.
- **At 3,000 and 4,000/s this laptop does not hold up.** Served throughput fell to about 476/s and 176/s, and
  the requests that were admitted waited 6-15 s (p95 of the 200s in the API log: 6.3 s at 3,000/s, 15.0 s at
  4,000/s): the Development queue of 1,024 is deep enough to hold several seconds of work. The transport
  failures are connections closed by Kestrel's 2,000-connection cap (47,514 `EOF` at 4,000/s) and Windows client
  listen-backlog refusals (1,804); k6 also hit its 4,000-VU ceiling. So "excess answered 503 within a second"
  holds for the 503s themselves, not for every excess request at these rates on this machine. Production's
  queue of 96 would bound the wait far lower; that was not measured.

## Run 4: login storm (new in v1)

**Guard mode** (`-ProductionLoginGuard`: PBKDF2 at 210,000 iterations, `LoginConcurrency=8`, `LoginQueue=16`,
every other login limiter opened up; ramp 5 → 40 logins/s over 2 m 20 s):

| Metric | Value |
|---|---|
| Logins accepted (200) / asked to wait (429) / wrong (401) | 3,146 / 3 / 0 |
| Successful sign-ins, averaged over the whole ramp | 22.4/s (the sustained 40/s phase was served with only those 3 × 429) |
| Login POST p50 / p95 / p99 / max | 197 / 536 / 600 / 640 ms |

On 16 hardware threads the guard barely engages at 40/s; Render's 0.1 vCPU would reach the queue much earlier,
which is what the guard exists for. This run does not measure that.

**Spray mode** (`LoginFailuresPerIpPer10Minutes=20`): 500 wrong-password attempts against 500 usernames from one
address got 20 × 401, then 429 from attempt 21 onwards (480 × 429). The genuine student `S000001` then signed in
from a second address with 200: the attacker was throttled and the victim's account was not locked.

## Log evidence

For every v1 run the API log was searched for `53300`, `40P01`, `42501`, "permission denied", "remaining
connection slots" and "deadlock" (as whole SQL states, not inside trace ids): zero matches, and zero
error-level lines. The PostgreSQL server log had no errors from these runs.

## Least-privilege rehearsal (before the load runs)

v1 had never run on a role without DDL rights, and production will. On a clone of the v0 database with
`rushday_app` granted exactly `docs/deployment.md` section 6, the API ran as in production
(`ASPNETCORE_ENVIRONMENT=Production`, KEK set, demo on and acknowledged, migrate and backfill on start, forwarded
headers trusted behind a local stand-in for Render's TLS proxy): the migrations ran on the owner connection, all
12 demo-mode backfills ran on `rushday_app` (and `demo_accounts_disable` on a demo-off start, 20,041 accounts),
`ANALYZE` ran on the owner, the encrypted Data Protection key was written, and the Playwright suite passed (57
passed, 3 skipped: account-creating journeys run on desktop only, 0 failed; per-user rate limits relaxed for the suite as in CI). No `42501` anywhere.
`rushday_app` was refused `TRUNCATE audit_events` and `CREATE TABLE`, as section 6 intends.
